# 消除多项目间代码重复的清单驱动重构

同一套服务端骨架被复制到多个独立项目里各自演化后，公共能力的重复实现带来的维护成本记录与解法。

## 一、背景与问题

同一套服务端骨架（配置加载、鉴权、路由注册、分片组装、自动更新等）被复制到多个独立项目里各自演化，形成了典型的「复制—粘贴式复用」。多个项目长期并行后暴露出一组相互纠缠的问题：

**1. 公共能力多份副本。** 同一模块在每个项目里各存一份，修一个缺陷要改多处，漏改一处就出现「某个项目已修、另一个还带病」的状态。

**2. 改动容易改错地方。** 没有权威副本，「这份改动该落在哪」全靠记忆。改在项目侧的公共代码，会在下次同步时被旧版覆盖，缺陷因此静默复活。

**3. 文件膨胀。** 单目录平铺了几十个文件，功能边界看不出来，新加一个模块只能继续往同一个目录里塞。

**4. 结果不可验证。** 上述问题都靠人工比对，没有可执行的一致性判据，改完之后无法回答「现在到底一不一致」。

## 二、思路

核心是**把「文件从哪来、到哪去」变成一份显式声明**，而不是靠约定和记忆。引入一份清单（JSON），逐条写明「来源 → 落点」：

```json
{ "server/framework/auth.js": "server/framework/auth/auth.js",
  "server/project/blueprint/login.html": "server/public/login.html" }
```

清单成为唯一真相后，几个难点自然化解：

- **公共能力只有一份权威副本**，落在模板仓库；项目侧由清单驱动同步。改公共能力就改模板，方向明确。
- **一致性成为可计算的**：清单两端逐文件比对内容，不一致/缺失都能自动报出。
- **结构可以随时重排**：改结构只需改清单，不必手工搬文件再逐个修引用。

配套解决三个具体环节：

**其一，重复度收敛。** 把公共骨架抽到模板仓库集中维护，各项目只保留自己的业务部分。每个功能在模板里只有一份实现，项目侧是它的投影。

**其二，结构按功能分层。** 平铺的公共目录按职责拆成子目录（核心/路由/HTTP/存储/配置/更新等），功能边界从目录结构直接可读，单个文件也不再无限制膨胀。

**其三，引用随结构自动修正。** 这是拆分后最容易被低估的一环——文件一旦换目录，`require` 的相对路径就全部失效。因此把「搬文件」和「改引用」作为**同一个动作**实现：按落点文件名配对后搬运，再自动重算受影响文件的相对引用，既包括被搬文件内部的引用，也包括**指向**被搬文件的那些外部引用。

对拿不准的情况（同名文件多个、配对顺序存疑）一律**报出让人工核对，绝不猜测搬运**——因为把文件搬错位置比不搬更难排查。

## 三、实际作用

按功能看，各命令解决的具体问题：

| 功能 | 实际作用 |
|---|---|
| **清单组装** | 按清单把素材产出到项目，公共能力不再各处复制 |
| **结构迁移** | 一条命令完成「搬文件 + 改引用」，实测迁移 22 个文件、自动改写 26 处引用（涉及 9 个文件），迁移后服务可直接启动 |
| **一致性检查** | 逐文件比对清单两端，回答「项目侧是否被改过、是否漏同步、是否缺失」 |
| **清单外扫描** | 扫整棵目录树，列出不在清单里的文件，并按 `.gitignore` 排除无关项——用于确认「该进清单的都进了」 |
| **素材回流** | 项目侧若有必须保留的改动，可预演并写回模板（写前备份），避免改动被同步覆盖而丢失 |

**整体效果：** 项目的公共能力收敛到单一权威副本，重复实现被消除；公共目录从平铺改为按功能分层，各项目结构一致；结构重排从「高风险手工活」变成可预演、可回滚、引用自动修正的常规操作；一致性由人工比对变为可执行判据，并能挂到 CI 上。

配套的工程约束也一并落实：迁移类破坏性操作先预演再执行、删除文件前确认 git 历史可恢复、文档只写「做了什么」而不含过程性表述。

## 四、小结

这次重构的关键不在于写了多少代码，而在于把**跨项目复用的隐性约定显式化**为一份清单，并围绕它补齐自动化能力。清单确立后，「改哪里、搬哪里、是否一致」都有了唯一答案；而把「搬文件」与「改引用」合并为原子动作，则消除了结构重排中最易出错、也最难排查的一环。
