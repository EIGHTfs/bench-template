# 组装反思：nexus-mod-downloader 首次组装不合格（2026-09-26）

> 本文件是「组装新项目」时的参考教训，写在 example 目录内，与 example/assemble.json
> 一起作为组装范本。新项目组装前先读本文件 + example/assemble.json，再动手。

══════════════════════════════════════════════════════════
📌 经验总结
- 现象：用模板组装 nexus-mod-downloader 第一版，服务能启动，但组装本身不合格——
  清单漏发框架件、前端分片残缺、路由重复实现，页面结构不完整。
- 根因：没先参考 example 组装方式就凭 gbmd 清单手抄；没跑漏发对照；
  学过的漏发体检方法（setup-assemble skill）没有应用到自己的组装。
- 解决：对照 example 清单补全（框架路由件 + 风格面板分片 + 混搭顺序），重组装后分片 8/8 完整。
- 防再犯：组装任何新项目前，执行文末「组装前检查清单」。
══════════════════════════════════════════════════════════

## 一、不合格点（三个具体错误）

### 错误 1：清单漏发框架件 `server/framework/route/routes-auto-update.js`

- gbmd 清单、example 清单都有这条（`routes-auto-update.js` → `server/route/routes-auto-update.js`），
  我手抄时漏了。
- 后果：`server/route/` 缺框架的自动更新路由组件；我在 `app.js` 里**手写了一份** auto-update
  路由（GET /status / POST /restart / POST /check）——与框架件重复实现，正是模板化架构
  最忌讳的「多处实现逻辑漂移」（example/README 与 setup-assemble skill 都强调框架件唯一实现）。

### 错误 2：前端分片残缺（页面结构不完整）

- `_downloader-style/fragments/` 只有基础分片（browse-mask / global-hud / head-extra /
  no-pwd-warn / tabs / topbar / styles），**没有 `scripts.html` 与 `tab-panel/` 四面板**。
- `index.html` 引用了 8 个 `@frag`（browse-mask / global-hud / head-extra / no-pwd-warn /
  scripts / tab-panel / tabs / topbar），第一版组装产物只到位 6 个——`scripts`（脚本注入）
  和 `tab-panel`（下载/进度/搜索/设置面板区）缺失，页面只剩空壳。
- 根因：以为「用一个风格整目录拷贝 fragments/ 就够了」，没验证「页面 @frag 引用 ↔ 组装产物」
  是否一一对应（example 的做法是：`_iwara-style/fragments/scripts.html` + `tab-panel/panel-*.html`
  作为业务骨架分片，明确列出）。

### 错误 3：brand 空 logo/icon

- 清单 `brand.logo / brand.icon` 给了空串，brand.json 生成空值，页面品牌区无图。
- example 的做法是给真实素材（`iwara-logo.png` → `server/public/iwara-logo.png`）并引用文件名。

## 二、根因分析

1. **没先读 example**：模板仓库自带 example 就是「组装范本」（README 明说「example/ 是模板自带的
   示例项目：它既是『组装效果长什么样』的参考，也是 test/ 脚本的测试对象」）。我直接抄 gbmd 清单，
   而 gbmd 是「下载器系 + 完整业务」的成熟项目，抄的时候丢掉了它清单里依赖的上下文。
2. **没跑漏发对照**：setup-assemble skill 里刚固化了「A 类漏发体检」方法（模板源 vs 清单声明对照），
   组装 nexus 时没有先跑一遍——skill 学了没应用（违背 skill-applies-past）。
3. **没验证页面完整性**：组装完只看「服务能启动」，没对照页面 `@frag` 引用与组装产物。

## 三、正确做法（重组装步骤，实测通过）

1. **先读 example**：`bench-template/example/assemble.json`（含 _comment 讲解混搭规则）
   与 `example/README.md`。
2. **清单骨架**：通用件（framework 全量 + lib/start.sh + blueprint/boot.cjs + cjs-bootstrap）
   + 蓝图公共件（theme-init / auto-update-card / config.schema.json 自研）+ 风格基础
   （`_downloader-style/public/*` + `fragments/`）+ **业务骨架分片**（`_iwara-style/fragments/
   scripts.html` + `tab-panel/panel-*.html` + `styles/row-thumb.css`）。
3. **混搭顺序**：同名分片「靠后的源覆盖靠前的」——风格专属覆盖条目排在基础条目之后。
4. **漏发对照**：组装前跑「模板源目录全部文件 vs 清单声明」对照（通用件 + 本项目使用的风格），
   确认 0 漏发。
5. **页面完整性验证**：`grep -o "@frag:[a-z-]*" server/public/index.html` 与
   `ls server/public/fragments/` 一一对应，缺一即不合格。
6. **组装 + 启动**：`./setup.sh --to <项目>/assemble.json` → `./start.sh start` →
   `curl /api/status`（200）→ 页面 HTTP 200（未设密码时为 302 → 登录页属正常）。

## 四、组装前检查清单（新项目必过）

```
□ 1. 读过 example/assemble.json 与 example/README.md（组装范本）
□ 2. 清单含 framework 全量（含 routes-auto-update.js）+ lib/start.sh + blueprint/boot.cjs
□ 3. 页面所有 @frag 引用 ↔ 组装产物一一对应（scripts/tab-panel 必须到位）
□ 4. 风格混搭顺序正确（覆盖条目在后）
□ 5. 漏发对照 0 项（模板源 vs 清单声明，含本项目使用的全部风格目录）
□ 6. brand 的 logo/icon 有真实素材或明确留空
□ 7. config.schema.json 存在（app.js 启动校验）且 port 不冲突
□ 8. ./setup.sh --check 两端一致；组装后 start.sh start 启动成功
```
