# 前端片段化改造指南

把整份 `index.html` 按功能拆成小片段，模板仓库按需组装（混搭）的设计与实测数据。

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 按 div 拆分可行吗 | **可行**，两个项目的 tab 结构完全一致（download/progress/search/settings） |
| 组装方式怎么选 | **服务端启动缓存 + mtime 热更新**（改片段刷新即生效，性能还比读单文件快） |
| 服务端 include 性能代价 | **每请求拼装只慢 3-4%**；启动缓存反而比读单文件快 48%（省磁盘 I/O） |
| 最大收益在哪 | 不是 374 行的 HTML，而是 **1983 行的 app.js**（本次先只拆 HTML） |

**2026-09-16 v1 已实现**：`framework/fragment-assembler.js`（mtime 热更新组装器）+
`createServer({ fragments })` 选项 + gbmd 前端拆 8 个片段落地验证。

**2026-09-16 v2 已实现（当前架构）**：双模板 diff 比对 → 共同框架抽到
`blueprint/index.html/downloader/index.html`（骨架 + `<!-- @frag:片段名 -->` 注释指令），
通用分片抽到 `blueprint/fragments/`，各项目特有分片留在自家 `fragments/`；
组装器扫描框架注释指令按相对路径插入片段 → 拼装结果与拆分前逐字节一致。

## 二、现状摸底（改造前必做）

### 2.1 前端规模

```bash
# gbmd 改造前
index.html   374 行   13K
app.js      1983 行   41K     ← 真正的大文件
style.css    386 行   8.5K
login/setup/其它 js  346 行
```

结论：HTML 只占前端总代码量的 15%，拆分 HTML 的收益主要在**可组装性**，不在减小文件。

### 2.2 结构与相似度（决定混搭可行性）

两个项目的 tab 结构完全一致：

| panel | gbmd | iwara | 共同 id | 可共用性 |
|---|---|---|---|---|
| download | 26 行 / 7 id | 19 行 / 5 id | 5 | 高（差异在字段） |
| progress | 36 行 / 20 id | 19 行 / 11 id | 10 | 中（结构同、字段异） |
| search | 49 行 / 25 id | 48 行 / 24 id | **22** | **极高（几乎一致）** |
| settings | 190 行 / 66 id | 143 行 / 38 id | 10 | 低（业务特有） |

**共同 id 比例是混搭可行性的直接指标**：search 的 22/25 共同 id 说明它几乎能直接共用；
settings 只有 10/66，说明它是项目特有块，只适合各自维护。

### 2.3 代码已有的可拆基础

- `app.js` 的函数已天然按功能分块：`bindSearch*` / `bindProgress` / `bindTask*` / `bindSettings*`
- `style.css` 已有功能分区注释（设置页块、任务行块、手机端适配块等）

拆分不是「重新组织代码」，而是「把已有的分区边界显式化」。

## 三、组装方式对比（实测数据）

### 3.1 基准脚本

```bash
node scripts/bench-html-assembly.js                          # 合成片段（6 片段 / 22KB）
node scripts/bench-html-assembly.js <真实 index.html 路径>    # 用真实文件规模
```

脚本对比三种方式：

| 方式 | 做法 | 运行时依赖 |
|---|---|---|
| `static` | 构建期拼好整份 index.html，运行时读单文件 | 无 |
| `assemble` | 服务端每请求读 N 个片段 + join | 拼装逻辑 |
| `cached` | 服务端启动时拼一次 + 内存缓存 | 拼装逻辑 + 缓存失效 |

### 3.2 实测结果（真实 gbmd index.html 规模，6 片段 / 21.6KB）

**串行 400 次**：

| 方式 | 中位延迟 | 平均 | 吞吐 |
|---|---|---|---|
| static | 464µs | 521µs | 1794 req/s |
| assemble | 420µs | 500µs | 1905 req/s |
| cached | **216µs** | **277µs** | **3361 req/s** |

**并发 600 次 / 30 并发**：

| 方式 | 平均 | p50 | p99 | 吞吐 |
|---|---|---|---|---|
| static | 13285µs | 11815µs | 90418µs | 2230 req/s |
| assemble | 13825µs | 12393µs | 87851µs | 2151 req/s |
| cached | **8966µs** | **7816µs** | **53360µs** | **3297 req/s** |

### 3.3 数据解读

1. **每请求拼装的代价是 3-4%**（2151 vs 2230 req/s）——因为 6 个小文件读完后 join 的成本，
   与读 1 个大文件几乎相同，瓶颈都在磁盘 I/O 与网络栈，不在字符串拼接。

2. **启动缓存比静态读文件快 48%**（3297 vs 2230 req/s）——省掉了每次请求的磁盘读。
   这是三类方式里最快的。

3. **对个人项目的实际意义**：本项目是单用户/低并发场景（自己用的下载器），
   p99 差异（90ms vs 53ms）远小于一次下载的耗时，任何方式都不会成为瓶颈。

4. **选择依据不是性能，而是工作流**：
   - 想要「改片段后刷新页面即生效」→ 选 `cached`（性能还更好）
   - 想要「产物是纯静态文件、服务端零逻辑」→ 选 `static`
   - **已定：cached + mtime 热更新**（改片段保存 → 刷新页面即生效，无需重启）

## 四、实现（2026-09-16 v2：蓝图框架 + @frag 注释指令）

### 4.1 目录结构（当前权威布局）

```
server/project/blueprint/index.html/downloader/index.html   ← 共同框架（骨架 + @frag 指令）【唯一权威】
server/project/blueprint/fragments/                          ← 通用分片（两模板相同块）
  tabs.html        tab 导航条（两模板逐字节相同）
  no-pwd-warn.html 未设密码警告（同，仅注释行差异）
  global-hud.html  speedHud + saveSettingsFab 悬浮按钮（同）
  browse-mask.html 目录选择弹窗（同）
server/templates/_gbmd-style/fragments/                      ← gbmd 特有分片
  head-extra.html  favicon 图标 + title（head 其余骨架在蓝图框架）
  topbar.html      顶栏（品牌区/登录徽章/时间/油猴/主题/退出）
  tab-panel/       ← 以功能块 class 为文件夹，id 为 html 文件名
    panel-download.html   27 行  下载面板
    panel-progress.html   38 行  进度面板
    panel-search.html     50 行  搜索面板
    panel-settings.html  191 行  设置面板（最大块，可再拆）
  scripts.html     页面脚本引用
  manifest.json    ← 行区间清单（split 工具用，来源=原整份 index.html）
```

模板的 `public/` 下**不再保留整份 index.html**（旧版已移入 `.trash-20260916-public-index/`）；
`fragments/` 与 `public/` 平级，setup.sh 组装时合并到目标 `public/`。

### 4.2 框架与 @frag 指令

蓝图框架只留骨架 + 注释指令，不写任何业务 HTML：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<!-- @frag:head-extra -->
<link rel="stylesheet" href="style.css">
<script src="theme-init.js"></script>
</head>
<body>
<!-- @frag:topbar -->
<!-- @frag:no-pwd-warn -->
<div class="container">
  <!-- @frag:tabs -->
  <!-- @frag:tab-panel/panel-download -->
  <!-- @frag:tab-panel/panel-progress -->
  <!-- @frag:tab-panel/panel-search -->
  <!-- @frag:tab-panel/panel-settings -->
</div>
<!-- @frag:global-hud -->
<!-- @frag:scripts -->
<!-- @frag:browse-mask -->
</body>
</html>
```

规则：

- 指令语法 `<!-- @frag:片段名 -->`，片段名可不带 `.html` 后缀（自动补）；
  子目录用 `tab-panel/panel-download` 形式
- 片段相对路径 = **相对片段根目录**（组装器 `dir`，即目标 `public/fragments/`）
- 组装器扫描框架 → 按指令读片段内容替换插入 → 输出完整页面
- 通用分片优先在 `blueprint/fragments/` 找，找不到再回退到项目特有 `fragments/`
  （同一指令名两者都定义了哪个生效？→ 由 setup.sh 合并顺序决定：特有覆盖通用）

### 4.3 组装器（framework/fragment-assembler.js）

支持两种模式（pages 值的类型区分）：

| 模式 | pages 值 | 做法 |
|---|---|---|
| **框架模式**（推荐） | `"index.html": "<框架文件路径>"` | 读框架 → 扫描 `@frag` 指令 → 替换插入；片段可分布在子目录 |
| 数组模式（兼容旧） | `"index.html": ["a.html", ...]` | 按顺序简单 join |

```js
createServer({
  fragments: {
    dir: <public>/fragments,          // 片段根（框架文件的相对路径也基于它）
    pages: { "index.html": <public>/index.html },
    watch: true,
  },
})
```

- **mtime 检测 = max(框架文件, 所有被引用片段)**，任一改动 → 下次请求自动重拼
- 缺失片段 → 替换为 `<!-- 缺失片段 @frag:xxx -->` 注释 + 回退旧缓存（不白屏）
- 命中缓存 ~9µs，重拼 ~48µs，比每次读单文件（18µs）快

**服务端接线**（app.js）：`loadFragmentManifest()` 改为「框架文件存在 + fragments/ 存在 → 返回框架模式 pages」，
不再依赖 manifest.json 的行区间数组。

### 4.4 与自动更新的配合（关键坑）

auto-update 的 watch 模式原本监控 `server/public/`，改片段会触发服务重启——
重启打断下载任务，抵消热更新价值。已修：

1. watch 排除 `public/fragments/` 与运行态 json（json/ 前缀、runtime-manifest 清单路径）
2. **框架文件 index.html 也排除重启**（app.js 实例化 `extraWatchExclude: ["index.html", "public/index.html"]`），
   因为改框架 → 组装器热更新，不需要重启

运行态排除清单通过**源码注释自动生成**（framework/marker-manifest.js）：

```js
//runtime-manifest.json file server/sessions.json watch=skip desc="会话持久化（登录态，运行期频繁写）"
//runtime-manifest.json file server/config.json watch=skip desc="服务配置（含密码/路径，本机权威）"
```

- 注释里写什么 json 名就生成什么 json（`userdata-manifest.json` 同样机制，供导入导出用）
- 支持 `key=value` 附加字段（`watch=skip`、`desc="带空格文本"` 引号值）
- data-backup 与 auto-update 共用同一套扫描逻辑，清单不会与代码脱节

### 4.5 setup.sh 组装（3b 段）

```bash
# 蓝图框架 → 目标 public/index.html（覆盖）
# blueprint/fragments/*.html → 目标 public/fragments/（通用分片）
# _${STYLE}-style/fragments/. → 目标 public/fragments/（特有分片，覆盖同名通用）
```

**组装发生在 setup.sh（拷贝时）**，运行期不再拼装；运行期只做 mtime 热更新
（组装器读到的已是合并后的完整 fragments/ 目录）。

### 4.6 拆分/拼回工具（往返验证用）

```bash
python3 scripts/split-html-fragments.py <index.html> <fragdir> <manifest.json>
python3 scripts/join-html-fragments.py  <fragdir> <manifest.json> out.html
diff <index.html> out.html   # 往返逐字节一致（md5 相同）
```

注意：split 最后一个片段会吸收文件尾部（browse-mask/body 等），
但这些块在 v2 架构里已属蓝图通用分片 → 分片后需手动截掉脚本/弹窗之后的尾部。

### 4.7 id 契约校验（待补脚本）

实测 gbmd 依赖关系：

```

index.html 提供的 id      133 个

```
