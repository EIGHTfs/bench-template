# 前端片段化改造指南

把整份 `index.html`（或 `style.css`）改造成「骨架 + `@frag` 片段」，由模板按需求组装、运行期热更新。
适用场景：多个项目共用同一套页面骨架，但各项目面板/顶栏内容不同。

## 改造后是什么样

```
templates/_downloader/html/index.html                  ← 框架：只有骨架 + @frag 指令
templates/_downloader/html/topbar.html                 ← 系级通用片段
templates/_downloader/html/tab-panel/panel-search.html ← 系级/项目片段（同名可覆盖）
server/public/fragments/                               ← 组装后的片段根（运行期读这里）
```

- 组装顺序：**通用片段先下发，项目特有片段后下发**，同名文件后写覆盖先写。
- 运行期不再拼装整份文件，只按 mtime 判断是否需要重拼。

## 改造步骤

1. **盘点规模**：先看 `index.html` 与 `app.js` 各多少行。HTML 拆分的收益是**可组装性**，不是文件变小；真正的大文件通常是 `app.js`，见 [组件化约定](20261014-JS组件化方案.MD)。
2. **划片段边界**：按功能块（head-extra / topbar / tabs / 各 tab-panel / scripts / 浮层）划分，边界与现有 CSS 功能分区对齐。
3. **切分并往返验证**：

```bash
python3 scripts/split-html-fragments.py index.html frags manifest.json
python3 scripts/join-html-fragments.py  frags manifest.json out.html
diff index.html out.html     # 必须无差异（逐字节）
```

4. **写框架**：框架文件只保留 `<!DOCTYPE>`、`head`/`body` 骨架和 `@frag` 指令，不写业务 HTML。
5. **归位**：通用片段上提到系级素材，项目特有片段留在项目层；两类片段最终落到同一 `public/fragments/`。
6. **接线**：服务端传入片段配置（框架模式）：

```js
createServer({
  fragments: {
    dir: path.join(publicDir, "fragments"),   // 片段根
    pages: { "index.html": path.join(publicDir, "index.html") },
    watch: true,
    brand: readBrand(serverDir),              // @brand:key 取值
  },
});
```

7. **组装**：清单里声明框架文件与片段目录的下发（`--dry-run` 先看落点）。
8. **验证**：拼回逐字节一致 → 真实渲染一次 → 改片段试热更新。

## `@frag` 指令规则

| 项 | 规则 |
| --- | --- |
| 语法 | HTML：`<!-- @frag:片段名 -->`；CSS/JS：`/* @frag:片段名 */` |
| 扩展名 | 不写，自动补 `.html`（CSS 片段写全名，如 `styles/variables.css`） |
| 子目录 | `@frag:tab-panel/panel-search` |
| 解析根 | 片段根目录（目标 `public/fragments/`） |
| 嵌套 | 支持递归，深度上限 8 层（防环） |
| 缺片段 | 插入可见的缺失注释并回退旧缓存，页面不白屏 |

## 装配器行为

- 两种页面模式：**框架模式**（`pages` 值是框架文件路径，推荐）与**数组模式**（值是文件数组，按序 join，兼容旧用法）。
- 热更新：mtime 取「框架文件 + 所有被引用片段 + 相关本地 js」的最大值，任一改动 → 下次请求重拼，运行中的服务不用重启。
- 资源版本化：装配时给本地 `<script src>` / `<link href>` 自动加 `?v=<内容 md5 前 8 位>`，脚本改一次 hash 变一次。
- 组装失败（片段缺失导致页面无法成形）返回 500 并打印原因，不返回半成品页面。

## 与自动更新的配合

- `watch` 模式**默认不因 `public/fragments/` 变化而重启**：片段改动由装配器热更新处理。
- 框架文件本身（`index.html`）建议用 `extraWatchExclude` 排除，改框架同样走热更新、不重启。
- 运行态与敏感文件的排除清单由源码注释生成（`templates/js/store/marker-manifest.js`）：

```js
//runtime-manifest.json file server/sessions.json watch=skip desc="会话持久化（登录态，运行期频繁写）"
//runtime-manifest.json file server/config.json watch=skip desc="服务配置（含密码/路径，本机权威）"
```

注释里写什么就生成什么清单，数据备份与自动更新共用同一份扫描逻辑，避免清单与代码脱节。

## 样式同样可片段化

`style.css` 也可以只留 `/* @frag:styles/xxx.css */` 骨架，按组件拆分配置。

## 已知限制

- 嵌套深度上限 8 层，超过即不再展开。
- 切分脚本按行区间工作，最后一段会吸收文件尾部（脚本引用、浮层等），切完需要人工截断再核对往返。
- **元素 id 契约没有内置校验脚本**：`app.js` 依赖的 id 与片段提供的 id 只能人工或自建脚本比对，缺 id 只在触发交互时报错。
- 片段化不改变运行时结构：仍是单页 + 全局脚本，不做模块化加载。

## 验收判据

1. 拼回结果与拆分前**逐字节一致**（忽略运行期注入的 `?v=`）。
2. 改任一片段或框架文件 → 刷新页面生效，服务**不重启**。
3. 真实浏览器渲染一次，交互元素齐全、控制台无报错。
4. 组装到目标项目后 `bash setup.sh --to <清单> --check` 报「清单两端一致」。
