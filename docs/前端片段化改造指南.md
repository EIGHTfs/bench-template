# 前端片段化改造指南

把整份 `index.html` 按功能拆成小片段，模板仓库按需组装（混搭）的设计与实测数据。

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 按 div 拆分可行吗 | **可行**，两个项目的 tab 结构完全一致（download/progress/search/settings） |
| 三种组装方式怎么选 | **推荐构建期静态拼接**；若要热改片段则用服务端启动缓存 |
| 服务端 include 性能代价 | **每请求拼装只慢 3-4%**；启动缓存反而比读单文件快 48%（省磁盘 I/O） |
| 最大收益在哪 | 不是 374 行的 HTML，而是 **1983 行的 app.js**（本次先只拆 HTML） |

## 二、现状摸底（改造前必做）

### 2.1 前端规模

```bash
# gbmd 改造前
index.html   374 行   13K
app.js      1983 行   41K     ← 真正的大文件
style.css    386 行   8.5K
login/setup/其它 js  346 行
```

结论：HTML 只占前端总代码量的 15%，拆分 HTML 的收益主要在**可组装性**，不在减小文件。

### 2.2 结构与相似度（决定混搭可行性）

两个项目的 tab 结构完全一致：

| panel | gbmd | iwara | 共同 id | 可共用性 |
|---|---|---|---|---|
| download | 26 行 / 7 id | 19 行 / 5 id | 5 | 高（差异在字段） |
| progress | 36 行 / 20 id | 19 行 / 11 id | 10 | 中（结构同、字段异） |
| search | 49 行 / 25 id | 48 行 / 24 id | **22** | **极高（几乎一致）** |
| settings | 190 行 / 66 id | 143 行 / 38 id | 10 | 低（业务特有） |

**共同 id 比例是混搭可行性的直接指标**：search 的 22/25 共同 id 说明它几乎能直接共用；
settings 只有 10/66，说明它是项目特有块，只适合各自维护。

### 2.3 代码已有的可拆基础

- `app.js` 的函数已天然按功能分块：`bindSearch*` / `bindProgress` / `bindTask*` / `bindSettings*`
- `style.css` 已有功能分区注释（设置页块、任务行块、手机端适配块等）

拆分不是「重新组织代码」，而是「把已有的分区边界显式化」。

## 三、组装方式对比（实测数据）

### 3.1 基准脚本

```bash
node scripts/bench-html-assembly.js                          # 合成片段（6 片段 / 22KB）
node scripts/bench-html-assembly.js <真实 index.html 路径>    # 用真实文件规模
```

脚本对比三种方式：

| 方式 | 做法 | 运行时依赖 |
|---|---|---|
| `static` | 构建期拼好整份 index.html，运行时读单文件 | 无 |
| `assemble` | 服务端每请求读 N 个片段 + join | 拼装逻辑 |
| `cached` | 服务端启动时拼一次 + 内存缓存 | 拼装逻辑 + 缓存失效 |

### 3.2 实测结果（真实 gbmd index.html 规模，6 片段 / 21.6KB）

**串行 400 次**：

| 方式 | 中位延迟 | 平均 | 吞吐 |
|---|---|---|---|
| static | 464µs | 521µs | 1794 req/s |
| assemble | 420µs | 500µs | 1905 req/s |
| cached | **216µs** | **277µs** | **3361 req/s** |

**并发 600 次 / 30 并发**：

| 方式 | 平均 | p50 | p99 | 吞吐 |
|---|---|---|---|---|
| static | 13285µs | 11815µs | 90418µs | 2230 req/s |
| assemble | 13825µs | 12393µs | 87851µs | 2151 req/s |
| cached | **8966µs** | **7816µs** | **53360µs** | **3297 req/s** |

### 3.3 数据解读

1. **每请求拼装的代价是 3-4%**（2151 vs 2230 req/s）——因为 6 个小文件读完后 join 的成本，
   与读 1 个大文件几乎相同，瓶颈都在磁盘 I/O 与网络栈，不在字符串拼接。

2. **启动缓存比静态读文件快 48%**（3297 vs 2230 req/s）——省掉了每次请求的磁盘读。
   这是三类方式里最快的。

3. **对个人项目的实际意义**：本项目是单用户/低并发场景（自己用的下载器），
   p99 差异（90ms vs 53ms）远小于一次下载的耗时，任何方式都不会成为瓶颈。

4. **选择依据不是性能，而是工作流**：
   - 想要「改片段后刷新页面即生效」→ 选 `cached`（性能还更好）
   - 想要「产物是纯静态文件、服务端零逻辑」→ 选 `static`

## 四、拆分方案

### 4.1 片段划分（按 tab-panel，4-6 块）

```
templates/_shared/fragments/       ← 两端可共用
  topbar.html                      ← 顶栏（用户名徽章/时间/油猴按钮/主题切换）
  modals.html                      ← 通用弹窗（toast/路径选择器）

templates/<style>/fragments/        ← 项目特有
  tabs.html                        ← tab 导航条
  panel-download.html
  panel-progress.html
  panel-search.html
  panel-settings.html
```

### 4.2 组装清单（manifest）

片段顺序不能靠文件名猜，需要显式清单：

```json
{
  "index.html": [
    "_shared/fragments/topbar.html",
    "tabs.html",
    "panel-download.html",
    "panel-progress.html",
    "panel-search.html",
    "panel-settings.html",
    "_shared/fragments/modals.html"
  ]
}
```

混搭时只改清单：iwara 若想用 gbmd 的搜索面板，把清单项指向另一份片段即可。

### 4.3 混搭的硬约束（id 契约）

拆分后最大的风险是 **id 契约被破坏**——JS 靠 id 找元素，片段缺失或改名会导致运行时静默失效。

实测 gbmd 的依赖关系：

```
app.js 依赖的元素 id      126 个
index.html 提供的 id      133 个
差集                        5 个（动态创建：toast 等）
```

**防错措施**（组装期校验，见 4.4）：

- 每个片段声明自己提供哪些 id
- 组装后校验「JS 需要的 id ⊆ 片段提供的 id ∪ 已知动态 id」
- 缺失即报错，不留到运行时

### 4.4 组装期校验脚本（设计）

```bash
# 组装后自动校验（setup.sh 调用）
node scripts/check-fragments.js <组装后的 public/ 目录>

# 检查项：
#   1. JS 里 getElementById 的 id 是否都能在 HTML（含片段）中找到
#   2. 片段清单声明的文件是否都存在
#   3. 是否有重复 id（拼接后同 id 出现两次）
```

## 五、分阶段实施建议

| 阶段 | 内容 | 风险 |
|---|---|---|
| 1 | 拆 `index.html` 为 6 个片段 + manifest + 组装脚本 + 校验脚本 | 低（产物与现在一致） |
| 2 | 拆 `app.js`（1983 行 → 按 panel 分文件，沿用已有的 bind* 分块） | 中（回归面广，需逐功能实测） |
| 3 | 拆 `style.css`（386 行 → 按功能分区） | 低 |

**阶段 1 的验收标准**：组装产物与拆分前的 index.html **逐字节一致**（用 diff 验证），
这样能确保拆分本身零风险，问题只可能出在后续阶段。
