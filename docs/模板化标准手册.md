## 第 1 章 油猴脚本入口链接参数化

约定「顶栏油猴脚本按钮」的链接从项目独有层上提为系级通用。

### 1. 现状：同一片段两份拷贝，仅 3 处差异

`templates/_downloader/_iwara/html/topbar/userscript.html` 与
`templates/_downloader/_gamebanana-mods/html/topbar/userscript.html` 内容结构完全相同，
仅以下 3 处不同：

| 维度 | iwara | gbmd | 处置 |
|---|---|---|---|
| href 脚本名 | `/iwara-cred-fetch.user.js` | `/gamebanana-cookie-userscript.user.js` | 参数化（见 §2.①） |
| href 版本号 | `?v=7.7.0`（与油猴元数据 @version 一致） | `?v=4.4.1`（元数据已 4.5.0，**已漂移**） | 去掉（见 §2.②） |
| title 文案 | 复制完整 Cookie 并一键发送 | 点击右下角 🍌 复制完整 Cookie（含 HttpOnly） | 参数化（见 §2.③） |

class / id / 内部结构 100% 相同（`class="btn ghost hbtn"`、`id="btn-userscript"`、
📥 图标 + 「油猴脚本」文本）——具备上提 `templates/_downloader/html/topbar/userscript.html`
系级通用的条件。

### 2. 方案选项

#### ① 脚本名参数化（二选一）

- **A（已确认）**：`href="/@brand:userscript@"`——相对路径整体一个键，项目在清单 brand 段填
  `"userscript": "iwara-cred-fetch.user.js"`。品牌值已全程走 `@brand:` 机制（运行期由
  `templates/js/config/brand.js` 从项目根 assemble.json 的 brand 段读取），一个键解决，最简。
- B：拆 `userscriptName` + `userscriptVersion` 两键——更细，但版本号现有 serve 端已防缓存
  （见②），拆版本键是反模式。

#### ② 版本号：html 一律不写（已确认）

**两个充分理由，双保险下 ?v= 完全多余：**

1. **serve 端已 no-store 防缓存（实测）**：两项目 .user.js 都是**路由 serve**（非 public 静态文件）——
   - gbmd `server/app.js`：`GET /gamebanana-cookie-userscript.user.js` → 读 `scripts/` 实体，
     响应头 `Cache-Control: no-store`
   - iwara `server/app.js`：`GET /iwara-cred-fetch.user.js`（含 `/userscript`、`/userscript.user.js` 别名）
     → 读 `scripts/` 实体，响应头 `Cache-Control: no-store`
   - no-store = 浏览器永不缓存，每次点链接都拉最新脚本，天然杜绝「装到旧版」。
2. **手写版本号已经漂移**：gbmd href `v=4.4.1` vs 元数据 `@version 4.5.0`——手写必然落后。

结论：href 不写 `?v=`，也不需要扩展 versionizeScripts（那是对 static 资源的方案，这里用不上）。
若未来某项目改为 public 静态 serve .user.js，再按 `<a href>` 纳入装配器 hash 不迟。

#### ③ title 文案（二选一）

- **B（已确认）**：title 也 `@brand:` 化（如 `@brand:userscriptTitle@`）——保留项目差异
  （gbmd 的 🍌 提示），代价是多一个键。
- A：上提后统一通用文案，放弃 🍌 差异。

### 3. 已确认组合（2026-09-28）

**①A + ②版本号 html 一律不写（serve 端 no-store 防缓存）+ ③B title 参数化**。

上提后片段形如：

```html
<a class="btn ghost hbtn" href="/@brand:userscript@" id="btn-userscript" title="@brand:userscriptTitle@" style="text-decoration:none"><span class="hbtn-icon">📥</span><span class="hbtn-txt">油猴脚本</span></a>
```

### 4. 待核实事项（已核实 2026-09-28）

- ✅ .user.js 由**路由 serve**（app.js 显式 GET 路由 → `scripts/` 实体），非 public 静态；
  响应头 `Cache-Control: no-store`。
- ✅ 版本号因此不需要（§2.②）。
- ⬜ 上提前再确认两份片段除 href/title 外无其它差异（class/id/结构已比对一致）。

### 5. 落地步骤（实施时执行）

1. userscript.html 上提 `templates/_downloader/html/topbar/userscript.html`，删两份独有层拷贝。
2. 清单 brand 段补 `userscript` + `userscriptTitle` 键；example/gallery/iwara/gbmd 各填。
3. iwara/gbmd/example 清单 src 键改到系级路径；重组装 + `--check` 两端一致。
4. 页面实测：点击按钮拉取到对应项目的 .user.js（no-store 生效、文件名正确）。

## 第 2 章 设置面板拆分（panel-settings → panel-settings/*.html）

讨论（2026-09-28）：`panel-settings.html` 不够细，可拆成 `panel-settings/*.html`，
部分卡片具有通用价值。**未动手，纯讨论记录。**

### 1. 现状：同一面板两份拷贝，内容差异大

| 项目 | 位置 | 行数 | 卡片数 |
|---|---|---|---|
| iwara | `templates/_downloader/_iwara/html/tab-panel/panel-settings.html` | 140 | 9 卡 |
| gbmd | `templates/_downloader/_gamebanana-mods/html/tab-panel/panel-settings.html` | 165 | 8 卡 |

- 引用方式：`index.html` 里 `<!-- @frag:tab-panel/panel-settings -->`（无扩展名自动补 `.html`）→ 当前是单个文件。
- 装配器支持**嵌套递归**（片段内还能再 `@frag`）→ 拆目录后总装文件内引用卡片即可，无需改装配器。
- 已有系级通用件范例：`templates/_downloader/html/auto-update-card.html`（两版本共用，即「设置面板内已通用化的卡片」）。

### 2. 拆分分析：卡片按通用度分三层

**① 完全通用（结构几乎相同）→ 可上提 `_downloader/`**

| 卡片 | iwara | gbmd | 差异点 |
|---|---|---|---|
| 修改密码 | newPwd + 按钮 | oldPwd + newPwd + 按钮 | 仅 iwara 缺 oldPwd（待确认：iwara 是否无初始密码场景） |
| 数据备份/恢复 | 导出/导入 zip | 导出/导入 zip | 结构 100% 相同，仅 hint 文案不同 |

**② 半通用（概念相同、项目细节不同）→ 拆出后参数化**

| 卡片 | 通用概念 | 项目差异（可参数化点） |
|---|---|---|
| 下载路径 | 下载根目录 + 路径浏览 | iwara 单根目录+文件名模板；gbmd 多游戏映射表 |
| Cookie / 凭证 | Cookie 输入 + 保存 + 检测登录 | iwara 凭证文本区 + 登录检测；gbmd Cookie 单行 + 保存按钮 |
| 保存按钮 | 设置保存 | iwara 面板底部统一保存；gbmd 每卡片独立保存（**设计分歧**） |

**③ 项目独有（留独有层）**

- iwara：点赞/关注、播放公开、下载后端（Aria2/CF IP/DNS）、视频索引
- gbmd：添加游戏、默认下载位置、文件夹合并/清空、角色映射、HTML 反查/重建索引

### 3. 关键设计分歧

1. **保存模型（已定：每卡片小保存，iwara 改造）**：
   - ❌ iwara 现状——面板底部一个「💾 保存设置」大按钮，整卡一次保存。
   - ✅ **统一为 gbmd 的「每卡片小保存」**：每张功能卡片自己的保存按钮（如「保存下载路径」「保存 Cookie」）。
     iwara 侧需要改造（拆掉底部大保存、按卡片拆分保存逻辑）。
   - 意义：半通用卡（下载路径/Cookie）共壳时保存行为天然一致；每卡独立保存也避免「误触整页保存」。
2. **通用件归属**：修改密码/备份两张纯通用卡上提 `_downloader/html/tab-panel/panel-settings/`（系级），
   总装文件（面板骨架）留各项目层引用它们——与 auto-update-card 模式一致。
3. **命名**：拆后 `panel-settings/` 目录 + 卡片名（`pwd.html`、`backup.html`、`download-path.html`），
   总装 `panel-settings.html` 保留作骨架，内部 `@frag:tab-panel/panel-settings/pwd` 嵌套引用——
   `index.html` 的引用不用改。

### 4. 建议（未确认）

**先只拆「完全通用」两张卡（修改密码、备份）上提验证链路**；半通用与保存模型分歧单独讨论，
不混进第一次拆分。

### 5. 待核实（已核实 2026-09-28）

- ✅ **iwara 不是「无 oldPwd 场景」，而是前端漏字段**（服务端支持，语义与 gbmd 一致）：
  - 服务端 `iwara-downloader/server/route/routes-auth.js:71`：
    `if (c.passwordHash && !cfg.verifyPassword(body.oldPassword || "", ...))` —— 已设密码后改密需校验旧密码。
  - iwara 前端 `panel-settings.html` 只有 `newPwd` 输入框、`app.js bindSettingsPassword` 只传
    `{ password }` 不传 `oldPassword` → **已设密码后改密会被服务端拒绝**（改密对老用户实际是坏的）。
  - 首次设置密码（`c.passwordHash` 为空跳过校验）→ 正常；`setup-init.js` 即首次设置模型。
  - gbmd 前端 `oldPwd + newPwd` 两框齐全，是完整实现。
  - **启示**：若「修改密码卡上提为通用件」，必须按 gbmd 的 `oldPwd + newPwd` 标准实现，
    iwara 前端需**补 oldPwd 输入框 + 调用传 oldPassword**（是修复不是仅上提）。

### 6. 实操完成（2026-09-28，iwara 改造）

- ✅ **iwara 补 oldPwd 字段**：`panel-settings.html` 修改密码卡加 `oldPwd` 输入框（「已设过才填」），

### 7. 实操完成（2026-09-28，修改密码/备份卡上提系级）

  `panel-settings.html` 总装骨架改为 `<!-- @frag:tab-panel/panel-settings/pwd -->` 嵌套引用。

### 2. brand 从清单读取（删 brand.json）

- 之前：组装时按清单 brand 段生成 `server/public/brand.json`，运行期 fragment-assembler 读 brand.json 替换 `@brand:key@`。
- 现在：**不再生成/读取 brand.json**。运行期由 `templates/js/config/brand.js`（模块导出 `readBrand(serverDir)`）从**项目根 assemble.json 的 brand 段**直接读取品牌配置。四个项目（example/iwara/gbmd/gallery）清单均已有 brand 段，组装后项目根 assemble.json 存在（运行期可读）；gallery 无 `@brand` 指令、不用 brand.js。
- 各项目 `server/public/brand.json` 已 git rm 删除。
- 收益：logo 改名只需同步清单 brand 段一处，不再有「brand.json 没跟」的静默碎图问题。

### 3. setup init 初始化复制删除
