# 清单驱动：跨项目复用的做法

同一套服务端骨架复制到多个项目里各自演化，随之而来四类问题：公共能力有多份副本、改动该落在哪靠记忆、结构重排靠手工、改完无法判断「现在到底一不一致」。
清单驱动的做法是把「文件从哪来、到哪去」变成一份显式声明，再围绕它补齐可执行的检查。

## 清单是什么

一份 JSON（`assemble.json`），逐条写明「来源 → 落点」：

```json
{
  "files": {
    "templates/js/auth/auth.js": "server/auth/auth.js",
    "templates/_downloader/html/tab-panel/": "server/public/fragments/tab-panel/"
  }
}
```

- **唯一真相**：清单里没声明的地方，项目里就不该有文件（`--untracked` 专门验证这一点）。
- **单一权威副本**：公共能力只在模板仓库维护一份，项目侧是它的投影；改公共能力就改模板。
- **一致性可计算**：清单两端逐文件比对，不一致/缺失都能自动报出。
- **结构可重排**：改结构只需改清单与素材位置，不必手工搬文件后逐个修引用。

## 五条配套能力

| 能力 | 作用 | 命令 |
| --- | --- | --- |
| 组装 | 按清单把素材产出到项目，同名后写覆盖先写 | `bash setup.sh --to <清单>` |
| 组装预演 | 列出「新增 / 覆盖 / 相同」，不写盘 | `bash setup.sh --to <清单> --dry-run` |
| 一致性检查 | 逐文件比对两端，回答「是否被改过 / 是否缺失」 | `bash setup.sh --to <清单> --check` |
| 清单外扫描 | 扫整棵树列出不在清单里的文件（按 `.gitignore` 排除） | `bash setup.sh --to <清单> --untracked` |
| 结构迁移 | 「搬文件 + 改引用」同一个动作，引用自动重算 | `bash setup.sh --migrate <旧清单> --to <新清单> --dry-run` |
| 素材回流 | 项目侧确实要保留的改动写回模板（写前备份） | `bash setup.sh --to <清单> --pull [--write]` |

迁移遇到同名文件多个、配对顺序存疑时**一律报出让人工核对**，不猜着搬：搬错位置比不搬更难排查。

## 做对了的判据

1. `--check` 报「清单两端一致」；`--untracked` 为空。
2. 迁移/重组装后服务能正常启动，公开端点有实际响应（不是「无报错」）。
3. 结构重排只改了清单 `src` 与素材位置，产物落点与引用不变。
4. 破坏性动作（迁移、回流、删除）都有 `--dry-run` / `--write` 分档，先预演再执行。
