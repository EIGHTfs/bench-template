# JS 组件化约定

把前端单文件产物（2000 行级 `app.js`）的**源码**拆成功能域分片，**产物**由组装期拼接生成。
运行时零变化：浏览器拿到的仍是单文件。

## 适用范围

| 适用 | 不适用 |
| --- | --- |
| 产物是单文件 `app.js`，不能改成 ES Module | 想引入打包器/前端框架 |
| 项目零依赖，不能装构建工具 | 需要 tree-shaking、代码分割 |
| 需要按功能域阅读、审查、限制单文件复杂度 | 产物本身已经是模块化加载 |

## 目录与命名

- 分片放在项目层的 `js/` 下，**目录 = 功能域**（不用 `parts/` 这类无语义名），与同名 CSS 同域：`modal.js` ↔ `modal.css`。
- `foundation/` 放跨分片共享的公共函数，**永远最先拼接**。
- `entry.js` 是入口（`init()` 总装），**永远最后拼接**。
- `manifest.json` 的 `parts` 数组是拼接顺序的**唯一来源**。
- `app.js` 是**产物**，由组装期生成，不手工维护。

两个项目层的现有布局可直接对照：

```
templates/_lumigather/js/                  templates/_downloader/_gamebanana-mods/js/
  foundation/ state i18n dom toast slug   foundation/ base
  shell/ tabs nav tree breadcrumb events  shell/ tabs theme lightbox
  browse/ images filtering folder render  download/ toggles batch control
  account/ login                          search/ form run poll results
  settings/ config settings category …    task/ view actions poll render row …
  entry.js  manifest.json  app.js(产物)   entry.js  manifest.json  app.js(产物)
```

分片数量随业务增长（约 20–35 片），按功能域切，不按行数切。

## 导出面与作用域

- **不改任何对外名字**：`window.*`、DOM id、事件绑定名、接口字段一律保持原样；分片只改源码组织。
- 有 IIFE 包裹的项目层：`foundation/` 的首片是 IIFE 开头、`entry.js` 是结尾帧，这两片单独拿出来不能通过 `node --check`，属正常现象。
- 没有 IIFE 包裹的项目层：每片都是独立合法 JS，可逐片做语法检查。
- **跨闭包共享的函数必须放 `foundation/` 且最先拼接**。放错位置不会报错，只在交互时抛 `ReferenceError`，语法检查与接口探测都发现不了。

## 拼接规则

| 规则 | 说明 |
| --- | --- |
| 顺序即依赖 | `manifest.json` 的顺序 = 源码顺序；顺序错 = 先拼接的片访问后定义的符号 |
| 一段一文件 | 同一文件不得对应两段**不相邻**代码（第二段会被挪到第一个位置；字节数可能仍正确） |
| 缺片即失败 | 片段缺失或清单损坏 → 拼接失败 → **中止组装**，不输出残缺产物 |
| 字节稳定 | 统一 LF、原子写（tmp + rename）、无时间戳，保证同一分片集产出同一字节 |

## 命令

```bash
# 生成产物
node scripts/join-js-parts.mjs templates/_lumigather/js/manifest.json templates/_lumigather/js/app.js

# 只比对不写盘（不一致退出码 1，可挂门禁）
node scripts/join-js-parts.mjs templates/_lumigather/js/manifest.json templates/_lumigather/js/app.js --check

# 也可直接给片段列表，不写清单
node scripts/join-js-parts.mjs --parts a.js,b.js out.js

# 组装项目时自动拼接（在拷贝清单之前）
bash setup.sh --to <项目>/assemble.json --dry-run   # 预演：列出将拼接的清单与产物
bash setup.sh --to <项目>/assemble.json             # 正式组装
```

## 改动流程

1. **只改分片**：定位到对应功能域文件；改 `app.js` 会在下次组装时被覆盖。
2. **新增功能**：新建分片文件 → 在 `manifest.json` 的 `parts` 里按源码顺序插入（公共层在前、`entry.js` 在最后）。
3. **自证**：`--check` 通过，或对产物做 sha256 比对（切分/移动片段后必须比，不能只看长度）。
4. **下游**：未重新组装的项目保持原状照常运行（各自提交了自己的产物）；重新组装写入同一份字节。

## 一致性判据

- 分片拼回的产物与基线**逐字节一致**（sha256）。
- `node scripts/join-js-parts.mjs … --check` 退出码 0。
- `bash setup.sh --to <项目>/assemble.json --check` 报「清单两端一致」。
- `test/js-parts.test.cjs` 覆盖空片段集、缺片报错、顺序敏感、重复运行幂等。

## 不要做的事

- **不要手改 `app.js`**：它是产物。
- **不要因为「同名」就把两个项目的组件改成一个样子**。例如两套 toast 在 DOM id/class、类型语义、时长、位置、配色、层级、移动端适配上共 11 个维度有 9 个不同，调用点合计 32 处——这是各自场景的合理设计，合并等于同时改两个产品的界面。
- **不要引入构建器**（esbuild/rollup 等）：会破坏零依赖，也超出「分片源码 + 拼接产物」的需要。
- **不要用行号切分**：按顶层函数/功能域归组，连续性由构造保证；切完必须自证。
