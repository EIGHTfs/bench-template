## 一、修改目标

- **问题**：两个下游项目的前端 JS 都是**单文件 2,000+ 行**（gallery `app.js` 2097 行 / gbmd `app.js` 2144 行），职责混杂；
  CSS 已按组件分文件（gbmd 19 个 / gallery 9 个）而 **JS 没有对应结构**；且 `base.css`/`toast.css`/`topbar.css`/`themes/`
  在**两个下游重复**。
- **期望**：
  - **A 阶段**：JS 变「**分片源码 + 拼接产物**」——**运行时零变化**（产物仍是单文件）。
  - **B 阶段（可选）**：在 A 之上做**真组件库**（共享层去重 + 统一组件接口）。
- **成功标准**：
  1. 拼接产物与切分前的单文件**逐字节等价**；
  2. 全部现有测试通过（含 `template-parity`）；
  3. 页面**渲染自检**通过（真实浏览器截图，不只是 API 通）；
  4. 审计中客户端复杂度 blocker（如 `rowHtml 51`）消失；
  5. **★ 下游仓库不重新组装也能继续正常工作**，重新组装后与模板逐字节一致。

### 2.2 为什么「不重新组装也能工作」（机制）

- 下游**各自提交**了 `server/public/*.js`（交付物入各自 git）⇒ **运行时完全不依赖模板仓库**；
- 模板只在下游执行 `setup.sh --to <清单>` 时被读取 ⇒ 模板改动**不影响**未重组的运行态；
- 因此 A 阶段的**逐字节等价**是下游安全的核心保证：重组 = 写入同一份内容，不重组 = 保持原状，**两种情况都正常**。

### 2.3 必须守住的四条

1. **映射路径不变**：`templates/_gallery/js/app.js`、`templates/_downloader/_gamebanana-mods/js/app.js` 仍是产物落点
   （`assemble.json` 不改键名/值），只是**产物改为组装期生成**。
2. **产物确定可复现**：同一分片集 → 同一字节（PART_ORDER 固定 + 统一 LF + 无时间戳/无随机）。
3. **`template-parity` 门禁必须继续通过**：模板产物 vs 下游文件逐字节一致（若不一致，说明下游没重组或产物漂移）。
4. **userscript / DSH 侧注入不受影响**：`build-userscript.js` 与 `fragments/topbar/userscript.html` 仍能取到所需片段。

### 2.4 下游验证（每步必做）

- 对 **3 个下游**各跑一次：`bash bench-template/setup.sh --to <下游>/assemble.json --check`（应报「清单两端一致」）；
- 对 **gbmd / gallery** 各跑 `node --test`（当前 gbmd 105/105、gallery 含 io-monitor/scan-async/template-parity 等）；
- 至少对 **gallery** 做一次**真实渲染截图**（用已修好的 browser 插件：`browser_open` + `browser_screenshot`）。

## 三、潜在问题分析

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| **作用域大坑** | **高** | 公共函数放错闭包 → **运行时 ReferenceError**，`node --check`/API 探测不到 | 共享层**最先**拼接；全部片段同一 IIFE；渲染自检必做 |
| 产物与源码双份 | 中 | 手改产物被 build 覆盖 | 产物**组装期生成**（照 `build-userscript.js` 先例），模板侧仍保留产物供下游取用 |
| 下游重组后行为变化 | 中 | 下游线上出问题 | **逐字节等价**为硬验收；每步对 3 个下游跑 `--check` |
| 模板回流遗漏 | 中 | 本会话已踩 3 次 | 走 `template-parity` 门禁；改模板再组装，**不直接改下游** |
| 零依赖被破坏 | 低 | 引入构建器 | 只用 node 内置，**禁用** esbuild/rollup/lit |

**边界条件**：① 空片段/单片段 → 退化为原文件；② 片段缺失 → **报错中止**（不静默少一段）；③ 并发组装 → 原子写；
④ CRLF/LF → 统一 LF；⑤ 下游存在本地改动时 `--check` 应报不一致（人工判断）。

## 四、Skill 学习检查

| 检查项 | 结果 | 说明 |
|---|---|---|
| 已有类似 skill？ | **有** | `dsh-clientjs-split-build`（分片 + 拼接 + PART_ORDER + 作用域坑，**本次主要依据**） |
| 同类问题方案？ | 有 | `module-splitter`（node 侧拆文件）、`func-index-targeted-read`（改前定位函数）、`zero-dep-nodejs-*` |
| 官方/社区做法？ | 有 | 原生 ES Module（**不适用**：两下游均非 module）、IIFE + 命名空间（**现状已在用**） |
| 现成库可用？ | 有但不用 | esbuild/rollup/lit 会破坏零依赖 |

**学习结论**：
1. **复用 `@frag:` 机制**——片段器正则 `/(?:<!--|\/\*)\s*@frag:([^\s]+?)\s*(?:-->|\*\/)/` **同时匹配 HTML 与 CSS 注释**，
   而 `/* @frag:x */` 在 JS 里是合法注释 ⇒ **JS 分片可直接用同一机制**，无需新造。
2. **复用 PART_ORDER 思路**：顺序即依赖，顺序不变 → 产物逐字节一致。
3. **共享层最先拼接**：跨闭包共享的公共函数必须放最前的共享片段（否则交互时才炸）。
4. **不引入任何依赖**；**不手改产物**。

## 十一、经验固化（硬要求）

**本次已可固化（写方案阶段就产生）**：

```
现象：需要给 JS 做分片机制，但项目零依赖、不能引构建器；准备新写一套 JS 片段器时，
      先读了现有片段器源码 fragment-assembler.js:15-18。
根因：该片段器的指令正则 /(?:<!--|\/\*)\s*@frag:([^\s]+?)\s*(?:-->|\*\/)/ 同时匹配
      HTML 注释与 CSS 注释；而 /* ... */ 在 JS 里是合法注释 ⇒ JS 天然可走同一机制。
解决：JS 分片直接用 /* @frag:片段名 */，复用既有片段器，不新造机制。
防再犯：**加机制之前先读现有实现的能力边界**（尤其正则/指令格式这类"看似只支持 A"的地方）。
```

落点：`dsh-clientjs-split-build`（追加一节「JS 片段可复用 HTML/CSS 片段器」）或
`bench-template/docs/模板化标准手册.md`（追加「JS 分片」章节）——执行阶段完成时一并落。
