# 旧项目模板化改造指南

把已有项目（扁平架构：自研 app.js + 路由 + 鉴权 + 静态文件）改造成模板架构
（framework + createServer/createRoute + 组装前端）的实操记录。

本文档记录**实际踩过的坑与对应解法**，供后续改造同类项目时直接对照。

---

## 一、改造目标与判断标准

**改造前（扁平架构）**：项目自带 app.js 装配 HTTP、自研鉴权/静态/路由分发。

**改造后（模板架构）**：
- `server/framework/` 提供 HTTP 服务、鉴权门、静态文件、路由工厂
- `server/app.js` 只做：建配置 → 定义业务路由 → 调 createServer
- `server/routes/*.js` 以 `createRoute({"METHOD /path": handler})` 形式导出
- 前端 `server/public/` 由模板 `setup.sh` 组装（可选，可后置）

**判断标准**：app.js 不含 `http.createServer`、不含鉴权/静态文件实现；routes 不含路径注册调用。

---

## 二、改造步骤（推荐顺序）

```
1. 建安全点        git tag + 备份 server/ 到 .trash（可恢复）
2. 同步 framework  cp -r <模板>/server/framework <项目>/server/framework
3. 补框架缺口      先解决「项目需要但 framework 没有」的能力（见第三节）
4. 改 routes       11 个文件：register(api) 形态 → createRoute 形态
5. 改 app.js       重写为 blueprint 形式（createConfig + createServer）
6. 处理 config/auth 对齐接口（见第四节）
7. 逐 API 实测     每个端点实测（见第六节）
8. 提交推送
```

第 3 步必须在第 4/5 步之前——否则改完 routes 才发现框架缺能力，要返工。

---

## 三、framework 缺口与扩展点（改造前先补齐）

扁平项目常见需求，通用 framework 默认不提供，需先扩展（扩展后对所有项目可用）：

| 项目需求 | framework 原状 | 扩展方式 |
|---|---|---|
| 公开路由（未登录可访问，如 `/api/status`） | 白名单硬编码 `[loginPath, "/api/auth/"]` | `createServer` 增加 `publicRoutes: ["/api/status"]`，并入鉴权白名单 |
| 未设密码时跳首次设置页 | 无 | `createServer` 增加 `needsSetup()` 回调 + `setupPath`，命中时静态返回 setup 页 |
| HTML 资源版本注入（防强刷） | 无 | `createServer` 增加 `transformHtml(html, pathname)` 钩子 |
| handler 需要 query 参数 | ctx 只有 `{cfg, auth, sendJson}` | `createRoute` 的 ctx 补 `query / pathname / params / url / req / res` |
| API 访问日志过滤（高频轮询不打日志） | 只有 `install/stamp` | `app-log` 补 `shouldLogApi(method, pathname)` + `apiLine()` |

**要点**：扩展点全部做成 `createServer` 的**可选参数**，不破坏已有项目调用。

## 四、接口对齐清单（改造中最容易踩的坑）

### 坑 1：`sendJson` 参数顺序不同 ⚠️ 高频

```
扁平项目：sendJson(res, 200, { ok: true })       ← status 在前
framework：sendJson(res, { ok: true }, 200)      ← status 在后
```

参数都是 number/object，**传错不报错但客户端拿到畸形响应**（status 位变成对象）。
机械替换（含括号配平，避免误伤多行表达式）：

```python
import re
PAT = re.compile(r'sendJson\(\s*res\s*,\s*(\d{3})\s*,\s*')
# 匹配后用括号配平找到第三参数结尾，重排为 sendJson(res, <expr>, <status>)
```

### 坑 2：handler 第三参数语义不同

```
扁平项目：(req, res, parsed)   parsed = url.parse(req.url, true)  → parsed.query.xx
framework：(req, res, ctx)     ctx = { cfg, auth, sendJson, query, pathname, ... }  → ctx.query.xx
```

替换：`(req, res, parsed)` → `(req, res, ctx)`；`parsed.query` → `ctx.query`。

### 坑 3：framework 的 routes 支持 prefix（会剥前缀）

`dispatchRoutes` 对 `{ prefix: '/api/auth', handler }` 会**剥掉前缀**再交给 handler：
handler 看到的 pathname 是 `/login` 而不是 `/api/auth/login`。

绝对路径注册的项目（路由键写全路径 `/api/settings`）→ 用 `prefix: ""` 组装。

### 坑 4：路由注册形态不同

```
扁平项目：route("GET", "/api/x", handler)        ← 命令式注册
framework：createRoute({ "GET /api/x": handler }) ← 表式导出
```

多行 handler 转换时，**不能按圆括号配平判断调用边界**（`(req, res) => {` 圆括号是配平的），
要按语句结尾 `);` + 花括号配平判断。脚本化转换易错，建议手工逐文件改。

### 坑 5：父目录 `"type":"module"` 导致 require 报错

零依赖项目不写 `package.json`，若位于 `"type":"module"` 目录树下：
- `node server/app.js` → `.js` 被当 ESM → `require is not defined`
- 用 `server/boot.cjs` 启动（`.cjs` 永远是 CJS），内部加载 `lib/cjs-bootstrap.cjs` 劫持本项目 `.js`

**排查陷阱**：用 `node -e "require('./lib/x.js')"` 测试会得到**空对象且不报错**
（Node 的 require(esm) 兼容路径），这在真实 boot.cjs 启动下不存在——测试必须走 boot.cjs。

### 坑 6：`readBody` 二次读同一请求 → 请求永久挂死（framework 级，影响所有项目）

**现象**：POST 请求发出去后 curl 一直挂着，服务端日志连 `[api]` 行都没有，进程活着。

**根因**：`createRoute` 在调 handler 前先 `parseBody(req)` 读了一次请求体（挂到 `req.body`），
handler 内部又 `await readBody(req)` 读第二次。Node 请求流只能消费一次，第二次永远等不到
`end` 事件 → Promise 永不 resolve → 请求挂死。

**修复**（已进 framework/http-utils.js）：`readBody` 加缓存，重复调用直接返回首次结果：

```js
function readBody(req, limit) {
  if (req._bodyCache !== undefined) return Promise.resolve(req._bodyCache);
  if (req._bodyPromise) return req._bodyPromise;
  req._bodyPromise = new Promise((resolve, reject) => { /* ... 读流 ... 成功后 req._bodyCache = parsed */ });
  return req._bodyPromise;
}
```

**排查提示**：凡是「请求无响应、无日志、进程正常」的现象，先怀疑请求流被读了两次。

### 坑 7：脚本转换会丢掉 `module.exports` 之前的模块级辅助函数

机械转换 `register(api)` → `createRoute({...})` 时，若只截取 register 函数体 + 其后的 tail，
放在 `module.exports` **之前**的模块级辅助函数（如 `gbCookieCred()`）会被整段丢弃，
表现为运行时报 `xxx is not defined`。

**防再犯**：转换后必须逐文件比对「原始版定义的每个标识符在当前版是否仍存在」：

```bash
for name in $(git show HEAD:server/routes/x.js | grep -oE "^(async )?function [a-zA-Z_]+|^const [a-zA-Z_]+ =" | awk '{print $NF}' | tr -d '=' | sort -u); do
  grep -q "\b$name\b" server/routes/x.js || echo "缺失: $name"
done
```

### 坑 8：鉴权门把公开端点也拦了（登录接口 401）

framework 的鉴权白名单默认只有 `[loginPath, "/api/auth/"]`。旧项目的登录端点是
`/api/login`（不在 `/api/auth/` 前缀下）→ 被拦成 401「未登录」，形成死锁。

**修复**：`createServer` 传 `publicRoutes: ["/api/login", "/api/logout", "/api/status"]`。

### 坑 9：未设密码时鉴权门先重定向，导致进不了首次设置页

旧项目语义是「未设密码 = 免鉴权」，framework 原实现先判鉴权再判 setup → 未登录被 302 到
login.html，永远到不了 setup.html。

**修复**：`dispatchAuth` 里加 `if (needsSetup()) return true;`（未配置密码阶段整体放行），
并在 `handleRequest` 里把 setup 页判定放到鉴权门**之前**。

### 坑 10：`config.get is not a function`

framework 的 `createServer` 假设配置管理器有 `get(key)`（createConfig 风格），
而旧项目自研 config 用 `readConfig()`。直接传会启动即崩。

**修复**：`createServer` 兼容两种风格，并支持显式 `port` 选项：

```js
const cfgPort = typeof config.get === "function"
  ? config.get("port")
  : (typeof config.readConfig === "function" ? (config.readConfig() || {}).port : null);
const port = portOpt || cfgPort || process.env.PORT || DEFAULT_PORT;
```

### 坑 11：`session cookie 名`与`createSession 返回值`不兼容

framework 的 `extractToken` 默认读 cookie `token`，旧项目用 `session`；
framework 的 `createSession({hours})` 返回 `{token, hours}` 对象，旧项目版返回 token 字符串。

**修复**：framework auth 的 `init({ cookieName })` 支持自定义 cookie 名（新增 `cookieName()` 读取），
调用方按对象解构 `const { token } = auth.createSession({ hours })`。

## 四之二、转换踩坑速查（做同类改造前先看这节）

| 现象 | 根因 | 一句话修复 |
|---|---|---|
| POST 无响应无日志、curl 挂死 | 请求流被读两次 | `readBody` 加缓存 |
| `xxx is not defined`（原本存在的函数） | 转换丢了 module.exports 前的辅助函数 | 比对标识符清单补回 |
| 登录接口 401 未登录 | 鉴权门白名单没有登录路径 | `publicRoutes` 加登录/登出 |
| 首页 302 到登录页、进不了 setup | 鉴权门在 setup 判定之前 | needsSetup 时整体放行 |
| 启动即崩 `config.get is not a function` | 配置管理器接口风格不同 | createServer 兼容 readConfig |
| 登录成功但后续 401 | cookie 名不一致（token vs session） | `auth.init({ cookieName })` |
| 静态资源版本号是负数 | `mtimeMs \| 0` 32 位溢出 | 改 `Math.floor(mtimeMs)` |

## 五、config / auth 对齐

| 扁平项目 | framework | 处理 |
|---|---|---|
| 自研 config.js（readConfig/writeConfig/setPassword/hasPassword） | `createConfig({configFile, schema})` | 业务特有方法（如 `normalizeDownloadToggles`）作为项目侧包装保留 |
| 自研 auth.js（loadSessions/startCleanup/extractToken） | `auth.init/createSession/isValidSession/extractToken/pruneExpired` | `startCleanup`（定时清理）在项目侧用 `setInterval(pruneExpired)` 补 |
| cookie 名自定义（如 `session`） | 需确认 framework 用的名字 | 对齐或作为参数传入 |

## 六、验证方法（改造后必做）

```bash
node --check server/app.js server/routes/*.js        # 语法
node boot.cjs &                                       # 启动（走 boot.cjs）
curl -s -o /dev/null -w "%{http_code}" .../api/status # 公开端点应 200
curl -s .../api/settings                              # 未登录应 401
# 登录后逐端点实测（登录/设置/游戏/搜索/下载/哈希/浏览/数据/合并/自动更新）
```

**验收标准**：每个 API 都有实际响应且结构与改造前一致（不是「无报错」即通过）。

**grep 级完整性检查**（防转换丢代码）：

```bash

  | awk '{print $NF}' | tr -d '=' | sort -u); do
  grep -q "\b$name\b" server/routes/x.js || echo "缺失: $name"

```

## 七、运行中的旧项目自动升级到模板版

**结论：能。** 已在模板化后的 gbmd 上实测验证（构造旧版部署 → 拉取新版 tarball 覆盖 → 启动）。

### 7.1 为什么能平滑升级

远端 tarball 是一个**自洽的完整快照**——`server/framework/` 与新版 `app.js` 同时存在，
旧版那时独有的 `server/auth.js` 在远端已删除。全量覆盖后就地变成完整模块版项目，
不存在「新 app.js + 旧 framework」的半截状态。

实测结果：

| 检查项 | 结果 |
|---|---|
| `server/framework/` 自动补上 | 已就位 |
| `app.js` 自动换成新版（160 行） | 是 |
| `server/config.json`（含密码/路径） | 排除清单保护，未覆盖 |
| 覆盖后启动 | 正常（`/api/status` 返回 200） |
| 更新后是否再次误覆盖 | 否，日志显示「首次运行，已记录基线版本…不执行更新」 |

### 7.2 两个前提（缺一不可）

**① 重启入口必须在新版的排除清单里**

GitHub 模式是「拉全量 → 覆盖 → 重启」，重启靠 `start.sh` / `server/boot.cjs`。
旧版若把远端旧版启动脚本一起覆盖，就会出现「重启变关闭」——服务再也起不来。

`GITHUB_EXCLUDE` 必须包含：

```
start.sh / start-linux.sh / start-macos.sh
server/boot.cjs
server/setup.sh
server/config.json
json/<运行态数据>
```

**② 首次运行必须只记基线、不应用更新**

无状态文件时 `state.lastSha` 为 `undefined`，若直接比较 `state.lastSha !== newSha`
恒为真 → 启动瞬间判定「有新版本」→ 全量覆盖 + 重启。

正确做法（已进 framework）：

```js
if (!state.lastSha && !state.lastCommitDate) {
  saveState({ lastSha: newSha, lastCommitDate: newDate, updatedAt: Date.now() });
  lastCheck = { result: "baseline", ... };
  return;   // 只记基线，不覆盖、不重启
}
```

### 7.3 已知残留：旧版独有文件不会被删除

GitHub 模式只做「覆盖 + 新增」，**不删远端已不存在的文件**。所以升级后：

```
server/auth.js     ← 旧版独有，新版已删 → 残留成孤儿文件
```

它是死代码（无任何 `require` 引用），不影响运行。介意可手动删：

```bash
mv server/auth.js .trash/     # 安全删除，可恢复
```

### 7.4 升级前的自检清单

```bash
# 1. 排除清单是否保护重启入口
grep -n "start.sh\|boot.cjs" server/framework/auto-update.js

# 2. 基线保护是否存在
grep -n "首次运行\|baseline" server/framework/auto-update.js

# 3. 远端快照是否自洽（framework 与新 app.js 同时存在）
curl -sL https://api.github.com/repos/<owner>/<repo>/tarball/main -o /tmp/v.tgz
tar -tzf /tmp/v.tgz | grep -E "server/framework/app.js|server/app.js"
```

三条都通过，运行中的旧项目即可安全自动升级。
