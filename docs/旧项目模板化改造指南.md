# 旧项目模板化改造指南

把已有项目（自带 `app.js` 装配 HTTP、自研路由/鉴权/静态文件）接入模板框架的实操步骤、接口差异与校验方法。

## 改造后的形态

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 服务装配 | 项目自己的 `app.js` 里 `http.createServer` | `createServer({ config, auth, routes, ... })` |
| 路由 | `route("GET", "/api/x", handler)` 命令式注册 | `createRoute({ "GET /api/x": handler })` 表式导出 |
| 鉴权/静态/HTTP | 项目自研 | 框架提供 |
| 前端 | 项目自带整份 `public/` | 由清单组装下发（可后置） |

**判据**：`app.js` 不含 `http.createServer`、不含鉴权与静态文件实现；`routes/*.js` 不含路径注册调用。

## 步骤（按顺序）

1. **留安全点**：打一个 git tag，把 `server/` 备份到回收站目录（可恢复）。
2. **同步框架素材**：按清单下发到项目，不手工抄框架文件。
3. **先补框架缺口**：项目需要但框架没有的能力先加（在第 4/5 步之前），否则改完 routes 才发现要返工。
4. **改 routes**：`register(api)` 形态逐文件改成 `createRoute` 表式导出。
5. **改 app.js**：重写为「建配置 → 声明路由 → `createServer`」。
6. **对齐 config / auth 接口**（见下表）。
7. **逐端点验证**（见「转换后校验」）。
8. **组装前端**（可选，可后置）。

框架扩展点（公开路由白名单、首次设置页、HTML 二次处理、ctx 字段、日志过滤）一律做成 `createServer`/`createRoute` 的**可选参数**，不破坏已有项目调用。

## 接口差异（逐项核对）

| 项 | 旧项目写法 | 框架写法 | 处理 |
| --- | --- | --- | --- |
| `sendJson` 参数 | `(res, 200, body)` | `(res, body, 200)` | 框架对两种顺序都兼容（第一个参数是数字时自动交换），新代码统一用 `(res, body, status)` |
| handler 第三参 | `(req, res, parsed)`，用 `parsed.query` | `(req, res, ctx)`，用 `ctx.query` | 改签名 + 换字段名 |
| 路由注册 | `route("GET", path, h)` | `createRoute({ "GET path": h })` | **手工逐文件改**：多行 handler 按 `);`+花括号配平判断边界，脚本转换易错 |
| 路由前缀 | 路由键写全路径 | `prefix` 会在分发前被剥掉 | 全路径项目用 `prefix: ""` 组装 |
| config | 自研 `readConfig()` | `createConfig({ configFile, schema })`，支持 `get()` | 框架兼容两种读法；项目特有方法在项目侧包装保留 |
| auth cookie 名 | 自研，常用 `session` | 默认 `token` | `auth.init({ cookieName: "session" })`；`createSession` 返回对象，按 `{ token }` 解构 |
| 读请求体 | 自行 `readBody(req)` | handler 前已读过一次 | 用框架 `readBody`：内部缓存，二次调用返回同一结果（重复读流会让请求永久挂死） |
| ESM 目录 | `node server/app.js` | 父目录 `"type":"module"` 时 `.js` 被当 ESM | 用 `server/boot.cjs` 启动（`.cjs` 恒为 CJS，再劫持本项目 `.js`） |

## 转换后校验

```bash
# 语法
node --check server/app.js server/routes/*.js

# 真加载（能发现语法与相对路径错误）
node -e "require('./server/routes/xxx.js')"

# 防脚本转换丢代码：原始版定义的每个标识符在当前版仍存在
for name in $(git show HEAD:server/routes/x.js \
  | grep -oE "^(async )?function [a-zA-Z_]+|^const [a-zA-Z_]+ =" | awk '{print $NF}' | tr -d '=' | sort -u); do
  grep -q "\b$name\b" server/routes/x.js || echo "缺失: $name"
done
```

验收标准：**每个 API 都有实际响应，且结构与改造前一致**——不是「无报错」即通过。

## 运行中的旧项目升级到模板版

覆盖式更新能平滑升级：远端快照是自洽的整体（框架与被更新的 `app.js` 同时存在），覆盖后就地变成模板版项目。两个前提：

1. **重启入口在排除清单里**：`start*.sh`、`server/setup.sh`、`server/config.json` 等被远端旧版覆盖会导致「重启变关闭」。
   `server/boot.cjs` **不在排除清单**——它是零依赖启动器、权威源在模板，需要随更新下发；更新流程是「先落盘校验 → 再重启」。
2. **首次运行只记基线**：无 `.auto-update-state.json` 时只写入 `lastSha` 并返回，不应用更新、不重启。

## 升级前自检

```bash
# 排除清单是否保护启停入口
grep -n "start.sh\|setup.sh\|config.json" server/update/auto-update.js

# 基线保护是否存在
grep -n "baseline\|首次运行" server/update/auto-update.js

# 远端快照是否自洽（框架与被更新的 app.js 同时存在）
curl -sL https://api.github.com/repos/<owner>/<repo>/tarball/main -o v.tgz
tar -tzf v.tgz | grep -E "server/update/auto-update.js|server/app.js"
```

三条都满足后，运行中的旧项目即可安全接受自动更新。

## 已知残留与限制

- 更新只做「覆盖 + 新增」，**不删除**远端已不存在的文件：旧版独有文件会残留成孤儿（无任何引用，不影响运行，可移入回收站）。
- 转换脚本只适合机械改参数顺序一类的活；路由形态转换请逐文件手改并对照原文件。
- 前端片段化是独立可选步骤，未做也不影响服务端改造结果。

## 常见故障速查

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| POST 无响应、无日志、curl 挂死 | 请求流被读两次 | 用框架 `readBody`（带缓存） |
| `xxx is not defined`（原本存在的函数） | 转换时丢了模块级辅助函数 | 比对标识符清单补回 |
| 登录接口 401 | 鉴权白名单没有登录路径 | `publicRoutes` 加 `/api/login`、`/api/logout`、`/api/status` |
| 首页 302 到登录页、进不了首次设置 | 鉴权门在 setup 判定之前 | 未设置密码时整体放行 |
| 启动即崩 `config.get is not a function` | 配置管理器接口风格不同 | `createServer` 兼容 `readConfig()`，或显式传 `port` |
| 登录成功但后续 401 | cookie 名不一致 | `auth.init({ cookieName })` 对齐 |
| 静态资源版本号异常 | 用 `mtimeMs \| 0` 造成 32 位溢出 | 时间戳取整用 `Math.floor` |
